# 长视频理解：百万级上下文（Long-Video Understanding at Million-Token Context）

> 一段 1 小时、4K 分辨率、24 FPS 的视频经过分块与嵌入（embedding）后，大约会产生 6000 万个 token。一期 2 小时的播客转录约为 30,000 个 token。一部完整的蓝光电影，即便经过激进的池化（pooling）压缩，也会有数十万 token。Google 的 Gemini 1.5（2024 年 3 月）开启了这一时代，以 1000 万 token 的上下文在数小时视频中可靠地完成“大海捞针”召回。LWM（Liu 等人，2024 年 2 月）展示了环形注意力（ring attention）的扩展路径。LongVILA 与 Video-XL 进一步扩展了视频摄取能力。VideoAgent 则用智能体检索（agentic retrieval）替代了原始上下文。每种方法都在计算、召回与工程复杂度之间做出了不同的权衡。本节课将把它们放在一起对比阅读。

**类型：** Build  
**语言：** Python（标准库，大海捞针模拟器 + 智能体检索路由）  
**前置知识：** Phase 12 · 17（视频时序 token）  
**时长：** 约 180 分钟

## 学习目标

- 计算不同帧率（FPS）与池化策略下长视频的视觉 token 总数。
- 解释三种扩展路径：暴力上下文（Gemini 1.5）、环形注意力（LWM）、token 压缩（LongVILA / Video-XL）。
- 对比原始上下文视频视觉语言模型（VLM）与智能体检索视频 VLM（VideoAgent）在准确率与延迟上的差异。
- 为一段 30 分钟视频设计大海捞针测试，并测量特定分钟位置的召回率。

## 问题背景

Qwen2.5-VL 尺寸的分块在 384 原生分辨率下，单帧约为 729 个 token。经过 3×3 池化后，每帧为 81 个 token。一段 30 分钟的视频以 1 FPS 采样，共 1800 帧，即 145,800 个 token。到 2025 年，开源 VLM 尚能处理，但已非常紧张。若提高到 2 FPS，则达 291,600 个 token——只有少数最大上下文模型才能装下。

一部 2 小时的电影以 1 FPS 采样为 58.3 万个 token。这超出了大多数 2026 年开源模型的能力；需要 Gemini 2.5 Pro 或更激进的池化。

三种扩展路径应运而生。

## 核心概念

### 路径 1：暴力上下文（Brute Context，Gemini 1.5、Claude Opus）

用硬件硬刚问题。将上下文扩展到数百万 token，在一次前向传播（forward pass）中处理全部内容。

Gemini 1.5 Pro 发布时支持 100 万 token；Gemini 1.5 Ultra 达到 1000 万；2026 年的 Gemini 2.5 Pro 已能可靠处理数小时视频。论文（arXiv:2403.05530）记录其在约 950 万 token 内的“大海捞针”召回率达到 99.7%。

工程实现：自定义的注意力（attention）实现，配合内存层级（局部 + 全局 + 稀疏）以及用于长上下文效率的混合专家（MoE）路由。细节未完全公开，亦非开源。

### 路径 2：环形注意力（Ring Attention，LWM、LongVILA）

环形注意力将长序列分布到多个设备上，形成一个“环”，每个设备保存一个块（chunk）。对完整序列的注意力计算通过每个设备将自己的块按环状发送给下一个设备、计算部分注意力（partial attention）并聚合来完成。

LWM（Liu 等人，2024）以此方式训练出支持 100 万 token 上下文的模型。训练计算随上下文长度线性扩展，而非二次方扩展——注意力的二次方开销被分摊到环中的多个设备上。

LongVILA（arXiv:2408.10188）将该模式适配到 VLM。1400 帧视频 × 每帧 192 token = 26.8 万上下文，通过 8 路并行（8-way parallelism）的环形注意力完成训练。

### 路径 3：Token 压缩（Video-XL、LongVA）

比暴力上下文更便宜：在 LLM 看到序列之前，先进行激进压缩。

Video-XL（arXiv:2409.14485）使用视觉摘要 token（visual summary token）：每个包含 N 帧的片段生成一个“摘要”token，该 token 对 N 帧进行注意力聚合。推理时，LLM 每片段只看一个摘要 token，从而大幅缩小上下文。

LongVA 则通过“长上下文迁移”（long context transfer）技术将 LLM 上下文从 20 万扩展到 200 万。先在长文本上训练，再通过共享表示迁移到长视频。

Token 压缩以牺牲特定时间戳的召回率为代价换取可扩展性。模型大致知道发生了什么，但有时会漏掉精确帧。

### 路径 4：智能体检索（Agentic Retrieval，VideoAgent）

不要把完整视频喂给 LLM。相反，将视频视为数据库，用 LLM 来查询它。

VideoAgent（arXiv:2403.10517）的流程：

1. LLM 读取问题。
2. LLM 向检索工具请求相关片段（例如“给我找有猫的片段”）。
3. 工具返回匹配片段的时间戳。
4. LLM 通过 VLM 读取这些片段。
5. LLM 组合答案，或提出后续查询。

这就是 LLM 作为智能体（LLM-as-agent）模式在长视频上的应用。推理更便宜（只编码相关片段），但工程更复杂（检索质量成为瓶颈）。

### 大海捞针基准测试

标准的长上下文测试：在视频中随机位置插入一个独特的视觉或文本标记（marker），然后提出一个需要召回该标记的问题。

评估指标：在不同视频长度和标记位置上的 Recall@k。

Gemini 2.5 Pro 在最长 90 分钟的视频中召回率超过 99%。开源 72B 模型（Qwen2.5-VL-72B、InternVL3-78B）在 30 分钟时约为 85–90%，超过 60 分钟后开始下降。

VideoAgent 在 2 小时以上视频中可以匹敌甚至超过原始上下文模型，因为只要检索工具足够好，就能命中“针”。

### 如何选择路径

- 15 分钟片段，追求前沿准确率：开源 72B + 原生上下文通常够用。选 Qwen2.5-VL-72B。
- 30 分钟到 1 小时内容：开源可选 LongVILA 或 Video-XL；闭源选 Gemini 2.5 Pro。质量要求高时优先闭源。
- 2 小时以上内容：VideoAgent 或类似的检索模式。也可以先压缩成小块，再喂入分层摘要。

### 2026 年生产实践模式

实际上，生产级长视频流水线是混合的：

1. 对整个视频运行动态 FPS 采样 + 激进池化（得到一个 10 万 token 的全局表示）。
2. 将其输入 72B VLM 生成全局摘要。
3. 当用户提出细节问题时，用摘要作为索引进行智能体检索。

这结合了暴力上下文的全局理解与检索对局部细节的精确定位。

## 关键术语

| 术语 | 人们的说法 | 实际含义 |
|------|-----------|---------|
| 暴力上下文（Brute context） | “就是更多 token” | 将 LLM 上下文扩展到数百万 token，一次处理全部内容 |
| 环形注意力（Ring attention） | “LWM 式并行” | 分布式注意力模式，每个设备保存一个块并旋转传递 |
| Token 压缩（Token compression） | “摘要 token” | 在输入 LLM 前通过可学习压缩器减少每片段 token |
| 大海捞针（Needle-in-haystack） | “NIH 测试” | 在随机位置插入独特标记，测试时让模型召回 |
| 智能体检索（Agentic retrieval） | “LLM 作为查询规划器” | LLM 向检索工具请求相关片段，经 VLM 阅读后组合答案 |
| VideoAgent | “视频检索模式” | 经典的智能体检索设计：问题 → 工具 → 片段 → 答案 |
